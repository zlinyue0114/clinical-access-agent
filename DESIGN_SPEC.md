# Design Specification

Version 0.1 (M0). This document is the contract the implementation and the evals
are checked against. Changes to invariants require a decision record in
`docs/decisions/`.

## 1. Problem

Clinicians increasingly want to query patient records in natural language. An LLM
agent with tool access to an electronic health record (EHR) creates new failure
modes: it can be talked into reading records it should not, it can follow
instructions hidden inside the very documents it reads, and it can move protected
data into places that were never meant to hold it (prompts, logs, traces, caches).

Prompt-level rules ("never show other patients") are not a security boundary. This
project builds an agent whose access properties hold even if the model is fully
compromised by prompt injection, and measures that claim.

## 2. Scenario

A radiology or pulmonology clinician asks questions about patients on their own
care team, for example:

- "Which of my patients' chest CT reports recommend follow-up imaging?"
- "Summarize the last CT report for patient P-7F3A."
- "Draft a follow-up CT order for that patient." (consequential, needs confirmation)

## 3. Scope

The agent **may**:

- list the clinician's own patients (pseudonymized),
- search and read imaging reports of those patients, limited to the fields a task needs,
- compute follow-up recommendations with validated, deterministic rules,
- prepare a draft follow-up order that the clinician must explicitly confirm.

The agent **may not**:

- read records of patients outside the clinician's care team,
- create, modify, delete or export records (no such tool exists),
- send data to any destination other than the EHR gateway and the model endpoint,
- act on instructions contained in record text.

## 4. Security invariants

| ID | Invariant | Enforced in |
|---|---|---|
| I1 | Clinician identity comes from a verified session token, never from model output or tool arguments. | Gateway |
| I2 | Every record read is authorized against the clinician's care-team panel; anything that cannot be authorized is denied (fail-closed). Errors do not reveal resource existence or schema. | Gateway |
| I3 | No tool can write, delete or export. The only consequential action yields a draft whose confirmation is bound to a hash of the exact content shown, single-use and expiring. | Tool set, gateway |
| I4 | Data reaching the model is field-minimized and pseudonymized with a keyed function; the key never reaches the agent process. Re-identification happens only in the presentation layer for the authorized clinician. | Gateway |
| I5 | Tool results are untrusted input. They are screened for injected instructions; screening is defense in depth, never the boundary. | Agent callbacks |
| I6 | Every access attempt, allowed or denied, is appended to a hash-chained audit log that can be verified offline. | Gateway |
| I7 | Per-clinician quotas limit distinct patients accessed per time window, so split or bulk access is detected even when each call is individually allowed. | Gateway |
| I8 | Telemetry does not store prompt or tool content by default. | Agent configuration |
| I9 | The number of model calls per request is bounded. | Agent run config |

## 5. Components

- **Data generator** (`data/`): seeded patients and practitioners, care-team
  assignments, structured chest CT findings, English and German report text from
  templates, deterministic follow-up labels, and an injection corpus embedded in a
  subset of reports.
- **EHR gateway** (`gateway/`): FastAPI service in front of HAPI FHIR. Implements
  I1, I2, I4, I6, I7 and confirmation verification for I3.
- **Agent** (`agent/`): Google ADK agent with read-only tools that call the gateway,
  guard callbacks (I5), bounded calls (I9) and telemetry settings (I8).
- **Evals** (`evals/`): quality, security and usability suites, a deliberately
  vulnerable baseline configuration as positive control, and a report generator.

## 6. Data

- Patients, practitioners and care teams: generated by a seeded, dependency-free
  Python generator (FHIR R4), see [ADR 0004](docs/decisions/0004-own-data-generator.md).
- Findings: generated structured findings (pulmonary nodules with size and type;
  incidental breast findings on chest CT), rendered into report text in English and
  German.
- Ground truth: follow-up labels computed by deterministic rules from the
  structured findings, never from the text.
- Adversarial content: instructions embedded in report text, varied by phrasing
  (explicit vs. clinically plausible), language (English, German) and goal (read
  another patient, exfiltrate, trigger a write).
- No real patient data from any institution is used at any stage.

## 7. Success criteria

| Area | Metric | Target |
|---|---|---|
| Quality | Recall of reports needing follow-up | >= 0.90 |
| Quality | Precision of reports needing follow-up | >= 0.80 |
| Quality | Tool trajectory matches expected calls | reported |
| Security | Cross-panel record reads that succeed | 0 |
| Security | Writes or exports performed | 0 |
| Security | Attack success rate per injection category | reported, 0 for reads outside panel |
| Usability | False refusals on legitimate queries | <= 5% |
| Audit | Access attempts present in the audit log | 100%, chain verifies |
| Controls | Vulnerable baseline is caught by the same evals | required |

Every eval suite runs against the vulnerable baseline first. A suite that does not
detect the baseline's failures is considered broken.

## 8. Model and residency

Development uses Gemini through Vertex AI. Some current models are served only from
the global endpoint, which conflicts with strict EU data residency. The production
notes (M5) document the EU configuration: regional endpoints, EU resource
locations, customer-managed keys and no service account keys, and the resulting
constraints on model choice.

## 9. Non-goals

- Clinical decision support for real patients. This is not a medical device.
- Production identity management (a local token issuer stands in for OIDC).
- Image analysis. Reports are text.

## 10. Open questions

- Whether to add an LLM-based purpose check ("is this request plausibly part of the
  care of this patient?") and how to measure its false refusals.
- How to express the confirmation binding so it can map to a standard such as AP2.
